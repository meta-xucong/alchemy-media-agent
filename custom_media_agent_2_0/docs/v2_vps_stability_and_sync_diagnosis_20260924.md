# V2 VPS 稳定性与资源同步诊断方案（2026-09-24）

## 目标

解决 VPS 偶发“暂时卡死后恢复”和资源同步只显示 `Permission denied`、无法定位失败文件的问题，同时保持现有 V2 生成、旧索引保护和 V2/V1 隔离行为不变。

## 已确认的事实

- VPS 主机约 2 GiB 内存，V1 容器在采样时约占 0.9--1.1 GiB，Swap 曾使用约 0.5--0.7 GiB；这足以造成短时响应变慢，但当前没有发现 OOM、hung task 或服务重启证据。
- 根分区约 94% 使用率；这是持续运行风险，不能通过删除历史 release、图片或缓存来掩盖，也不属于本补丁的自动清理范围。
- `sshd`、UFW、Fail2ban 均正常，`MaxStartups` 未显示打满；SSH 日志主要是正常登录和客户端主动中断，暂不能把 SSH 间歇性失败归因于应用代码。
- `resource_sync_worker` 原来只输出异常的 `repr`，因此同步日志无法回答“哪一个路径、哪一个 errno、哪一阶段失败”。
- 现有同步失败路径已经是安全的：保留之前有效的 case index，不发布不完整索引。本次不改变这个状态机。

## 权威层与最小修复

### 1. 同步服务是资源索引状态的权威层

`sync_resource_provider` 继续负责获取、解析、写入和发布索引；写入失败必须返回失败状态并保留旧索引。新增统一异常摘要，仅补充诊断字段：异常类型、errno、失败路径和第二路径（若底层异常提供）。

### 2. worker 是运行观测层，不改变业务决策

worker 在未处理异常处记录结构化摘要和 traceback。它不增加无限重试，不绕过远端同步，也不把异常转换成质量审核失败。这样下一次真实同步可以直接区分 GitHub 下载、快照写入、索引替换或缩略图预热阶段。

### 3. 资源压力先观测、后调整

在没有时间序列和峰值证据前，不给 V1 随意增加 worker、不强行限内存、不重启服务。VPS 侧先采集 `free/vmstat/docker stats/journal`；只有确认峰值与具体进程后，才单独设计运行参数变更。磁盘历史数据清理属于运维审批事项，本代理不执行删除。

## 验收标准

- 本地 V2 资源同步相关回归通过，新增用例验证 `PermissionError` 的类型、errno、路径被保留。
- 对普通异常，仍保持既有失败码、可重试标记和旧索引安全回退。
- 发布后执行一次受控的单次远端同步；若成功，确认索引版本、服务状态和旧数据未被破坏；若失败，日志必须给出明确阶段/路径，而不是只有 `Permission denied`。
- 资源采样没有 OOM、服务反复重启或持续不可回收的 Swap 增长后，才评估 VPS 运行参数优化。

## 非目标

- 不修改提示词、图像审核或二维码后处理逻辑。
- 不通过降低审核标准、无限重试或删除旧数据解决稳定性问题。
- 不在本补丁中改变 SSH、UFW、Fail2ban 策略。
