# V3 项目读取与主服务恢复

## 事故与修复边界

2026-11-24，手机版登录成功后，V2 历史等待 8 秒超时。VPS 堆栈显示主线程在 V3 完整详情中逐条构造旧任务的公开状态。触发项目有 24 条任务，任务文件约 569 MB。独立 V2 服务仍能响应。完整详情曾由 FastAPI 的同步路由调度到工作线程。提交 `56519246` 将路由改为异步鉴权，留下同步详情调用。后续只隔离了摘要和部分图库请求。以前的生图并发、图库吞吐和首屏测试各自有效，均未检验重型完整详情期间的主服务可用性。

## 开发方案

1. 保留各读取接口的响应。完整详情、项目内图库和时间线都会保存协调后的项目状态，它们与硬删除共用一个工作线程，以保证读取被浏览器取消时，仍在写的请求能先结束。旧记录大于图库计算池的 4 MiB 上限时也不会落回事件循环。全局图库继续使用现有计算池，摘要、首图预览、健康检查、V2 和生图沿用现有入口。已打开项目所需的单任务读取也移出事件循环。
2. 完整详情在同一次读取内复用已经计算的历史任务状态和图片列表。正式交付列表只构造一次，复核图片和来源说明继续使用现有规则。手机版首屏和桌面普通打开使用原有摘要和缩略图。已有收藏、选中参考、当前操作及专业模板需要的字段通过兼容详情保留。手机版历史超时沿用现有中文提示。
3. 由 VPS 上的 systemd 定时器探测现有本地 `/healthz`。健康时只发一个轻量请求。连续失败后才取已有发布锁，复查健康并使用现有在途任务清点。清点空闲且容器仍为同一实例时，受控重启主容器，检查重启后的健康状态。启动宽限与重启间隔避免连续重启。维护、任务在途及任务状态无法确认时暂缓，由日志记录原因。已有 Bridge 任务、API 未知结果和扣费归原记录处理。

读取优化属于 V3 基础运行层。项目、图片和任务的鉴权、视觉审核、交付决策和扣费沿用现有规则。健康探测独立于用户请求。上线沿用现有候选与受保护激活流程。

恢复流程复查的是运行中容器的 ID、启动时刻和最后一次健康状态。探测和重启动作之间存在极短的请求竞态，原任务的持久化和禁止自动重放规则继续兜住该窗口。启动宽限为 120 秒，同一主机两次自动重启至少间隔 300 秒。运行日志通过 `journalctl -u alchemy-media-agent-watchdog.service` 查看。回滚到没有恢复脚本的历史版本时，systemd 的路径条件会跳过探测服务。

## 验收

- 在本地隔离环境阻塞 V3 完整详情，验证同一 ASGI 服务的健康和 V2 历史能先返回；释放后验证原详情响应、权限与图片状态。使用多条历史任务证明同一详情的列表复用。
- 模拟短暂故障、主服务卡死、发布互斥、在途任务和恢复失败，验证空闲时重启一次、长故障时受重启间隔限制。
- 本地通过后推送 GitHub，经 CI 和候选镜像检查后激活 VPS。核对主服务、H5、V2 和恢复定时器。使用已有项目和图片做只读验收。
