# 隔离验证与索引维护交接

## 适用范围

本轮改动不是旧进程 RAM 导出工具，也不是 VPS 切换授权。PR #28 的迁移协议及其尚未核实的生产前置条件继续有效。生产运行版本、旧进程内存状态、数据库与文件备份必须由另一次获授权的切换核验确认，不能从 GitHub 合并状态推断已部署。

新增的 V1/Lab 表是派生读模型；业务 Job、Output、Session、manifest、owner evidence、收藏与文件仍是原权威。禁止通过清空业务表、删除 JSONL、伪造 import receipt 或放宽 owner 检查修复索引。

## 本地/CI 复核顺序

1. 固定待审提交和工作树状态，保留用户已有修改；在干净隔离 worktree 复核。
2. V1 与 V2 使用各自声明的 Python 依赖环境。两者包名均为 `app`，不可在同一解释器中混合加载。V2 按 `pyproject.toml` 安装依赖并从其源码目录运行，不能因其现有 flat layout 打包失败而修改本轮无关的 packaging 结构。
3. 先运行新增索引、查询计划、归属、队列取消和双端需求加载测试，再运行原权限/删除/导入/Lab suites、完整 V1 API smoke 与 V2 suite。
4. `tests/test_sqlite_read_admission.py` 同时覆盖两份独立 pool 实现；`tests/frontend_demand_history.test.mjs` 执行实际发布函数的需求/取消/账户切换合同。Node VM 测试不是完整浏览器视觉验收。
5. 使用 `scripts/benchmark_history_reads.py` 生成临时合成夹具和报告。新脚本可通过 `--repo` 指向固定旧基线，从相同夹具定义比较优化前后。必须分别指定 V1/V2 解释器，不使用生产路径、真实账号或 Provider。

示例（解释器路径替换为本地隔离环境）：

```sh
python scripts/benchmark_history_reads.py \
  --v1-python /venv-v1/bin/python --v2-python /venv-v2/bin/python \
  --sizes 100,1000,10000,50000 --concurrency 2,4,8 \
  --rounds 50 --output /tmp/history-read-optimized.json
```

详细计数以单独 `--diagnostic` 运行采集，不把插桩耗时当正常请求延迟。若旧实现 50,000 行单次需较长时间，可用较少旧基线样本记录重复工作量；不足 100 个成功样本时不声明 p95。失败/503 和正确性结果必须同时交付。

## 受控派生索引维护

`scripts/prepare_v1_history_index.py` 必须显式提供已有存储目录。它不启动 API、生成任务、Provider 或后台 worker。该命令只在操作者已核实目标目录和维护范围后运行；本轮开发仅对合成临时目录执行。

- `--prepare`：构建缺失的派生索引或追赶已提交的来源变更。
- `--rebuild`：根据当前 SQLite 权威和文件库存重建派生表；不重新播放已导入 JSONL，不清理业务记录。
- `--reconcile`：受控扫描文件库存，核对外部添加、移除、变更；这是明确 O(文件/manifest 数) 的维护，不是每次列表请求的隐式工作。
- `--verify`：以 SQLite 只读连接检查派生版本/待处理项、必要触发器、悬空来源引用及计数桶双向一致性。它不导入旧文件、不修复数据；`derived_internal_coherence` 仅证明这些内部约束，不证明与任意外部改动后的全部权威逐字一致。
- 首次旧 JSONL 导入仍受原严格导入协议约束；维护命令不得偷偷替代未完成的业务导入或伪造完成标记。

首次构建/重建持有 SQLite 写事务，可能影响其他写入。应提前在获授权的维护时段准备，记录耗时、数据库/WAL 增量和磁盘余量；不能把冷构建计入热页性能后宣称每次都很快。返回 `catch_up_pending` 或 `blocked` 不等于完成。

维护前若需要备份，必须取得一致的 SQLite 快照并覆盖关联文件；不能只复制活跃数据库主文件而遗漏 WAL。数据库备份和恢复不由上述索引工具自动执行。

V1/Lab 索引绑定实际存储根目录。将数据库复制到另一存储根后，旧库存不能直接复用；必须在核实新目录内容后显式重建，避免访问旧路径。索引引用的路径也必须处于当前 generated 根内。

V2 计数桶由同一数据库事务内的触发器维护，首次初始化受写事务保护。应用管理的连接启用 recursive_triggers，覆盖 INSERT OR REPLACE 的隐式删除；绕过管理连接的手工 SQL 不在此保证范围内。维护函数 verify_history_counts 使用只读快照核对计数，rebuild_history_counts 仅重建派生桶；两者是 O(N) 维护，不是热列表动作。派生版本、结构或计数一致性异常返回经脱敏的 503，不以扫描整个历史的回退掩盖故障。

## 错误与恢复

- 读队列满或准入等待超时：原有 503 与 `Retry-After: 1`。最多两个已提交工作、六个待执行读请求，等待上限 250ms；该上限不是正在执行 SQL 的超时。
- 索引版本/结构异常、持续变化或文件修复达到上限：明确不可用，修复或受控维护后重试。不得回退到将 owner 不明或冲突数据公开的路径。
- 外部改动未被观察到的文件仍以最后提交库存为准。页内检查只能发现访问到的缺图，不能保证全库即时磁盘计数；新增孤立文件需要核对。
- 回退代码前先评估 SQLite 触发器与派生表的前后版本兼容。不要通过随意删除派生表留下指向缺失表的触发器；不要触碰业务权威。版本回退不是本轮自动操作。

## 最终交接必须填写的证据

- 固定 SHA、分支、PR 状态、CI 对应 SHA，以及本地/远端一致性。
- 每组测试命令、通过/失败/跳过数量；重叠套件不相加。
- 100/1k/10k/50k、2/4/8 矩阵的正确性、成功/503、冷构建/热页延迟与资源报告。
- 单记录变化的增量刷新、超过 10k 的旧记录、跨 session 归属冲突、删除重试和缓存失效证据。
- 明确保留 `risks-and-boundaries.md` 的既有归属发布窗口、深 OFFSET 成本、用户主动全量收藏筛选和 VPS 未验收边界。旧的 V2 热页 COUNT 扫描已由计数桶替代，维护验证仍需扫描。

代码与合成负载通过只能支持本轮实现范围。完整浏览器操作、真实 Provider、生产迁移、VPS 容量和上述既有安全窗口没有测试或修复时，必须继续标注未完成。
