# Alchemy API 与 MCP 接入方案（仅做适配）

> 后续用户明确新增「用户创建 API Key / 管理员概览」，已按 45 号文档增加绑定原账户的可撤销访问凭证。本文「不新建 API Key」是前一阶段范围，不再禁止该明确新需求；账户、登录、余额、计费及 V3 业务流程仍不重建。
> 状态：精简定稿 v0.3，2026-09-25；本轮只改方案，不改代码。
> 原则：给现有程序增加调用方式，不改程序的业务机制。
> 本版替代 v0.2 的开发范围；前版提出的新账户、API Key、访问层、任务及结算建设，不纳入本次任务。

## 一、最终方案

**API 复用现有 HTTP 接口；MCP 将这些接口包装成 Codex 可调用的工具。账户、登录、权限、计费、任务、生成、审核和存储全部沿用现有系统。**

```text
现有 Web ───────────────┐
脚本 / 第三方应用 ──────┼→ 现有已鉴权 HTTP 接口 → 现有 V3 业务流程
新增产品级 MCP 工具 ────┘

已有本地规划 / Materialization MCP：继续原来的冻结与 handoff 链路。
```

不增加新业务服务，不要求现有 Web 改接另一套入口。API/MCP 的增加不改变同一账户的资源归属、费用规则或图片交付标准。

## 二、API 怎么做

直接整理并复用 `/api/v3/creative-agent/...`，提供必要的调用说明、请求示例和错误说明。首版不新增 `/api/v1`，不做路径迁移或 OpenAI 兼容接口。

对外只说明现有产品操作：创建项目、上传素材、发起生成、查询进度、获取结果、选择输出。后台管理、内部冻结合同和本地 handoff 不随之开放。

请求字段、素材用途、模板选择、返回状态及分页规则沿用现有接口；缺少示例就补文档，不为统一命名重写合同。

现有异步流程怎样返回 `project_id`、`operation_id`、`job_id`，适配后就怎样使用。不另建 generation_id、队列、状态机或恢复系统。

## 三、登录和计费怎么接

**登录：使用已有账户及现有登录方式取得合法凭证。** API 客户端按现有接口要求发送会话凭证；已有 Bearer Session 可直接按现有方式使用。MCP 从本地配置取得该账户的合法凭证，不另建 API Key、OAuth、租户、作用域或账户表。

适配器不自动读取浏览器 Cookie 或索取账户密码；凭证通过用户授权的配置提供，不放进提示词、工具参数、URL 或日志。凭证失效时返回现有登录提示，不匿名继续、不代填其他账户。

**计费：正常调用现有生图入口，由原有业务链完成余额检查和扣费。** 适配器只传递当前账户身份及原有必要字段，不自行估算收费、不再扣一次、不建立新的余额或结算记录。失败、退款、额度不足等行为沿用原规则。

复用的是当前实际生效链路，不是挑一个同名函数替代。通过 Web 与 API/MCP 的同账户对照确认权限与费用一致；发现接错入口，修正适配调用，不扩成账户或计费重构。

## 四、MCP 最小工具集合

产品工具通过配置的现有 Alchemy 服务地址调用上述 HTTP 接口，保留原入口的鉴权和业务处理，不直接操作 Provider 或 Store。已有低层 MCP 工具不改名、不改执行合同。

| 工具 | 复用能力 |
| --- | --- |
| `alchemy_create_project` | 现有项目创建；返回原 project_id |
| `alchemy_upload_asset` | 现有上传、内容写入及完成流程；返回原 asset_id |
| `alchemy_create_generation` | 在指定项目中按现有 Web 异步方式创建并生成 |
| `alchemy_get_generation` | 按项目规划记录或 job_id 查询现有进度 |
| `alchemy_list_outputs` | 读取现有项目/Job 输出及其状态、下载入口 |
| `alchemy_select_outputs` | 调用现有选择接口，不直接写 winner |

上传只读取用户明确授权的本地文件，将内容传给已有上传接口；不把本机路径当成服务器路径。需要下载时返回原鉴权下载入口，由同一凭证访问，不另建公开分享链接。

创建工具走现有 `auto_generate` 流程后，不再补发一次 `/generate`。规划未产生 Job 时保留原 operation_id，通过原项目查询继续观察，不创建替代任务。

工具返回原 ID、业务状态和必要结果，可压缩说明但不重新判断“成功”“通过”或“可交付”。查询不能创建任务；写请求超时不能盲目重发，先利用现有 ID/操作记录确认状态。

首版不封装尚未明确需要的取消、续作、批量导出或专业模块管理。后续有具体使用场景，再逐项包装已有能力。

## 五、只保留必要边界

1. API/MCP 使用相同账户走原有鉴权，不能通过工具参数伪造 owner、审核结果或内部控制字段。
2. 生成、审核、选择、推荐与下载继续使用现有规则；待复核不等于失败，也不等于已交付。
3. 已有本地 `mcp-materializations` 保持 loopback-only，nonce、Prompt/素材 hash、消费与恢复规则不变；不因业务 API 可访问就将其公开。
4. 本地低层工具按原合同取得冻结 Prompt 和获准素材；新增产品工具不向调用者暴露服务器路径、密钥或原始 handoff 合同。
5. 不自动改变监听地址、反代、认证开关或生产配置来接通接口；本次是适配，不包含公网部署改造。

## 六、改动落点与实施顺序

**第一步：整理现有 API 的使用方式。** 核对登录凭证携带方式和六类操作的实际请求/响应，补最小示例。现有 HTTP 接口能完成就不新增后端接口。

**第二步：在现有本地 MCP 适配目录增加产品工具封装。** 优先复用已有 HTTP 调用方式；必要时只增加 `product_tools.py` 等小型适配文件，并在现有 MCP 入口注册。不新建公共 API 框架或重复的鉴权、计费、存储模块。

**第三步：验证适配等价性。** 先用受控测试确认参数、身份和调用次数，再用同一账户跑少量真实端到端用例。不用真实付费生成反复调试工具协议。

现有程序如果已能处理某能力，直接调用；暂不支持的能力明确返回原限制，不借这次任务补一套业务机制。确有阻断接入的问题，先说明具体入口与最小修正，不默认扩大范围。

不做：新 API Key/登录体系、独立计费/配额系统、新队列/幂等服务/状态机、新审核投影体系、组织权限平台、Webhook、正式 SDK、远程 MCP 网关和核心代码重构。

## 七、验收标准

| 验证项 | 通过条件 |
| --- | --- |
| 登录与权限 | 原账户可正常调用；无效/过期凭证、其他账户资源仍按原规则拒绝 |
| 生成闭环 | 上传→项目→生成→查询→结果→选择可走通；不额外创建 Job 或重复提交 |
| 费用一致 | 与 Web 使用同一收费链；相同输入和执行条件下无额外扣费，无绕过余额检查 |
| 结果一致 | 对同一 Job，Web、API、MCP 的任务状态、推荐结果、复核和交付结果一致 |
| 既有 MCP | 原规划、冻结、handoff、恢复与一次性消费回归不被破坏 |
| 改动范围 | 只增加调用说明及适配代码；无新的账户、计费、任务、审核或存储体系 |

源码依据：既有路由及鉴权见 `src_skeleton/app/main.py`；产品服务见 `alchemy_creative_agent_3_0/app/product_api/` 与 `app/project_mode/`；本地工具与 HTTP 桥见 `services/alchemy_codex_local_adapter/mcp_server.py`、`materialized_bridge.py`。本次据此复用，不把文档方案当成已经实现的功能。

## 八、可转发总结

这次只做接入适配，不改 Alchemy 的业务机制。API 直接复用现有 V3 HTTP 接口并补调用说明；MCP 将项目、上传、生成、查询、结果和选择包装成工具。账户登录、权限、余额、计费、任务、审核和存储全部走原有流程。已有本地 Codex 规划与 handoff 保持不动，不开放内部本地接口。先把最小闭环跑通，验证与 Web 的身份、费用和结果一致，不建设新的 API 平台或业务系统。
