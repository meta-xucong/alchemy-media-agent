# V1 / V2 Queue Lease and Async Admission Correction

Date: 2026-10-08
Reference and target baseline: PR #26 head `7ef7e602ee215f4f5624ba2f7e3c55157709ba25`
Scope: V1 session-image admission, V2 queue claim/output fencing, and Alchemy Lab capacity/history admission. This document does not extend the V3 plan or authorize deployment.

## Objective and correction model

The complete task is to close the independently reviewed runtime defects on top of PR #26 while preserving normal API behavior, durable queue identity, retry semantics, and local capacity coordination. The current phase is implementation and deterministic regression coverage; passing it does not establish VPS capacity or production readiness.

The code-level mismatch is that the V1 session-message image path can leak a capacity exception as a server error, and `/v1/image/jobs` takes a generation slot before resolving an idempotent replay; V2 queue claims have no attempt-specific ownership token or active-task heartbeat; a worker that loses its V2 claim during provider work can still write an image job, files, history, or a billing debit; stale insufficient-balance preflight writes process-local records before the claim recheck; and concurrent API/worker schema initialization can race additive column migration. Synchronous SQLite acquisition, enqueue, and cleanup can block async request loops; V2 direct admission treats future retries and every running row alike, which can starve direct work or all spare slots. Alchemy Lab begins intent planning before reserving its shared generation lease, and its history route scans JSONL synchronously inside an async handler.

The owning layers are: V1 route error projection and idempotency admission; V2 durable queue state, schema initialization, claim-fenced preflight/result persistence, generation admission, and local result commit; and bounded async persistence adapters at V1/V2 async boundaries. Alchemy Lab acquires the shared SQLite lease before intent planning and retains it through inline/background generation; its history route uses existing bounded scan admission. The existing SQLite queue remains the authority for V2 task state and V1/V2 SQLite leases remain local, same-filesystem coordination only. Attempts continue to represent retry budget; they are not claim identities. A random claim token fences each attempt. Task heartbeat remains active through preflight, provider work, and terminal persistence. Worker ownership is rechecked before billing and inside an immediate transaction around local V2 output/job/history writes, so queue takeover cannot overlap that local commit. A provider request already in flight cannot be remotely canceled by this local fence.

Queue ordering is explicit: due queued work and a fresh worker claim that has not acquired a generation slot take priority over new direct requests. A fresh running task that already holds a queue-associated generation slot consumes that slot but does not block spare slots in a multi-slot configuration. A queued retry with a future `not_before` does not block direct admission. Terminal rows do not block admission. Enqueue, claim, and direct/worker slot acquisition continue to serialize through the same SQLite database and immediate transactions.

SQLite operations called from async routes use a finite, fail-fast offload admission bound. Saturation or local storage contention returns a retryable service-busy response. Cancellation waits for an in-flight local acquisition and releases any lease acquired after cancellation; operation cancellation retains its lease until the local provider coroutine finishes. Cleanup errors are logged and do not turn a successful generation into a retryable generation failure. These guards bound local threads and database work; they do not prove that a remote provider stopped or guarantee remote exactly-once execution.

## Implementation boundaries

- Additive SQLite migration only: claim token/generation and `success_checkpoint_json` columns on `v2_tasks`; association columns on `resource_leases`. Queue table creation, column checks, additive `ALTER TABLE`, and index creation run in one `BEGIN IMMEDIATE` transaction so API and standalone workers serialize first-time migration against the same file. Preserve terminal queue rows, retry evidence, and all user history. Do not add TTL/LRU deletion or background queue cleanup. A superseded V2 attempt cannot enter the local result commit transaction; only its uncommitted, empty `running` job placeholder is removed from the in-memory repository. Completed jobs, outputs, and history are never evicted by this guard.
- Keep V2 provider and billing network calls outside SQLite write transactions. Recheck claim ownership after balance preflight and immediately before every initial/fallback provider request; check again after provider return and before billing. Hold the short local claim transaction across output materialization, repository save, history append, usage recording, and the successful task checkpoint. Queue retries use one Veyra idempotency key and reference ID per task so retry request identity stays stable. Existing tasks billed by old code with per-job keys are not retroactively reconciled; drain/reconcile outstanding tasks before a future rollout. Remote calls already in flight cannot be canceled or atomically rolled back with local SQLite.
- A successful V2 image-job save can write `success_checkpoint_json` in the same claim-fenced SQLite transaction. It replaces the matching job in the latest queued run snapshot and writes a completed run only when every generation job in that snapshot is completed. The worker checks this checkpoint before preflight/provider work, rehydrates the entire run and every job/output projection under the replacement claim, and then attempts terminal queue finalization three times with short bounded delays. Successful finalization stores `result_json` and clears the checkpoint atomically. Stale checkpointed rows remain reclaimable even after the ordinary attempt budget is exhausted; reclaiming a checkpoint does not consume another generation attempt. Missing checkpoints follow the normal generation path. Invalid JSON, wrong-run, incomplete, truncated, or inconsistent job/output manifests are rejected and never treated as success; the expected job manifest is cross-checked against `queued_run_json`.
- Keep V2 independent of V1 modules and V1 storage. Keep V1 image session flow and Veyra ownership checks intact.
- Resolve V1 image-job idempotency before taking the generation lease. The preflight is side-effect-free and uses the same derived key plus capacity-retry fingerprint as the submit service. Active/completed replays return the existing job; a matching retryable capacity failure still needs a lease to restart generation; a genuinely new request remains retryably rejected at capacity.
- Persist a V2 insufficient-balance preflight's local job/run projection inside the same immediate claim-fenced operation used for local result persistence. A stale preflight returns without leaving unreferenced repository records; the queue row remains the authority for the public run projection.
- Validate explicit Alchemy Lab style IDs against the local catalog and validate the requested style count before admission, then hold its existing same-host SQLite lease before intent planning and retain ownership through inline generation or transfer it to the bounded background task. The existing `MAX_CONCURRENT_GENERATIONS` limit and retryable 429 response remain unchanged. This does not claim cross-host admission or guaranteed cancellation of a remote planning request.
- Preserve the V2 API response schemas and current retry budget. V1 image-session capacity exhaustion becomes HTTP 429 with `Retry-After: 5`, a stable `generation_capacity` error code, and `retryable=true`; chat/video behavior remains unchanged.
- Default standalone and inline worker IDs become process-instance identities. Startup no longer releases rows by a reusable worker label. A claim is recoverable only after its heartbeat becomes stale; every takeover receives a new token.
- Do not rewrite providers, infer remote cancellation, or claim cross-host/global capacity. API and workers must continue to share the configured `V2_TASK_QUEUE_DB_PATH` on the same host/filesystem.

## Configuration

- `RESOURCE_DB_ASYNC_WORKERS`: default `4`, clamped to `1..16`; bounds SQLite work offloaded by each V1 or V2 process. Each process has its own bound; this is not a cross-process or generation-capacity limit.
- `V2_TASK_QUEUE_SQLITE_BUSY_TIMEOUT_SECONDS`: default `5`, clamped to `0.1..30`; bounds each V2 task-queue SQLite busy wait. It does not change claim/retry semantics.
- Existing generation settings remain authoritative: V1 `MAX_CONCURRENT_IMAGE_GENERATIONS` and `GENERATION_CAPACITY_LEASE_TTL_SECONDS`; V2 `V2_MAX_CONCURRENT_IMAGE_GENERATIONS`, `V2_GENERATION_CAPACITY_LEASE_TTL_SECONDS`, `V2_TASK_QUEUE_CLAIM_TIMEOUT_SECONDS`, `V2_TASK_QUEUE_MAX_PENDING`, and `V2_TASK_QUEUE_MAX_ATTEMPTS`. Alchemy Lab uses the existing `MAX_CONCURRENT_IMAGE_GENERATIONS` lease across intent planning and generation; its history route shares `HISTORY_SCAN_MAX_CONCURRENT` (default `2`).
- API and standalone V2 workers must use the same `V2_TASK_QUEUE_DB_PATH` on the same host/filesystem. A process-local semaphore cannot coordinate them. SQLite-backed admission coordinates processes only when they actually share that local database; it is not a cross-host guarantee.

## Compatibility, migration, and rollback

The schema change is additive and initialized with `CREATE TABLE IF NOT EXISTS` plus column checks inside `BEGIN IMMEDIATE`; concurrent new-version API/worker initializers serialize on the SQLite write lock and then re-check the columns. Existing task identity, snapshots, result/error data, and terminal rows remain readable. Existing rows with no claim token are not eligible for token-fenced writes by the new worker; recovery waits for the configured stale-claim timeout and then creates a new claim token. Before a rolling deployment, stop or drain old worker processes: old code does not understand claim tokens and can still issue unfenced updates. This PR does not perform a VPS rollout or migration against live data.

Rollback may restore the previous application code while leaving the extra SQLite columns in place. Do not delete or recreate the task database during rollback. If migration/worker rollout is later performed, preserve a database backup and validate queue recovery and shared-path configuration first.

## Follow-up corrections reproduced after PR #26

The follow-up review started from PR #27 head `7acadcfab8b8caacb901ce1dfed9e6b00a97d732`. Three defects were reproduced with temporary SQLite data and fake providers; none demonstrates a VPS or production incident:

1. A successful V2 generation could be persisted in the repository while the terminal queue write hit SQLite busy. The worker returned from the claim-heartbeat context, leaving the queue row `running` with no `result_json`; after the claim became stale, a replacement worker called the runtime/provider again. A bounded finalization retry alone was insufficient if every finalization attempt remained locked.
2. When claim takeover occurred during the awaited Veyra balance preflight, the old worker still entered the provider before its existing post-provider claim check. The fake provider was called after the claim had already moved to a new worker.
3. An Alchemy Lab background task canceled before its coroutine body executed skipped the coroutine's `finally`, leaving its cross-session SQLite lease heartbeat alive. Cancellation after the coroutine started already released through `finally`.

The queue fix adds the additive `success_checkpoint_json` field. The image job, local output/history/usage effects, and checkpoint write run under the current claim-fenced SQLite transaction boundary; filesystem writes are not rolled back with that transaction. The versioned checkpoint carries job and output manifests. Recovery validates them against the embedded run and the authoritative `queued_run_json` job set, checks that each job belongs to the run and each output belongs to its job, and rejects incomplete or inconsistent records. The checkpoint's top-level `prompt_plan` comes from the first completed job, matching the normal final `CreativeRun` after prompt transformation and integrity preflight. If terminalization gets SQLite busy, the same worker retries three times; once it gives up, the heartbeat stops and a later claimant restores the whole run from the checkpoint without re-running orchestration, generation, balance preflight, or billing. The checkpoint keeps every completed job and output, including output owner and task idempotency metadata. It does not invent success from one listed completed job while another job in the authoritative snapshot is queued or running. `get_run_snapshot` also projects the committed success checkpoint while queue terminalization is pending, and falls back to the queued snapshot if checkpoint validation fails.

Generation now rechecks the active claim immediately after balance preflight and after awaited fallback-provider selection, immediately before each outbound image-provider call. The existing post-provider check still prevents stale billing and local result writes. Alchemy Lab transfers a one-shot lease owner to each scheduled task: the runner marks itself started at entry and releases in `finally`; the task done callback schedules one bounded async cleanup when cancellation happened before entry. If scheduling itself fails, the caller retains ownership and releases from its existing `finally` path.

There is no distributed transaction between SQLite and the local filesystem. Output files, JSONL history, and usage evidence are written before the checkpoint's SQLite commit. A process crash after those file writes but before the checkpoint commit can leave orphaned local artifacts and the queue may retry generation because it has no authoritative checkpoint. Once the checkpoint commit succeeds, a retry restores its complete serialized result and does not repeat provider or billing work. This does not promise remote exactly-once generation, nor does it repair a missing output file after an external filesystem loss. A corrupt or incomplete checkpoint is never surfaced as success: the claim-fenced worker terminalizes it with a non-retryable integrity error while preserving the raw checkpoint for diagnosis, avoiding a repeated generation/billing loop.

The queue recovery test builds a two-job completed run with owner and billing-idempotency metadata, forces all three terminalization attempts to report SQLite busy, simulates process-local repository loss, and confirms the next claim reloads both jobs and outputs without invoking preflight/runtime or changing the existing usage record. It also verifies the effective job prompt plan and timestamp survive recovery, that a checkpoint consistently truncated in both its run and embedded job manifest is rejected against the authoritative queued snapshot, and that missing output data or an output/job mismatch is not accepted. Separate coverage verifies that an incomplete multi-job snapshot is not checkpointed, invalid JSON is not success, and a missing checkpoint remains absent. The provider-window regression forces a claim replacement during balance preflight and asserts zero provider calls. Lab coverage includes cancellation before first execution, cancellation after start, normal return, and an exception, with one lease release in each case.

The current queued creative-run runtime creates one generation job per task, and that job may contain multiple outputs. `CreativeRun.generation_jobs` can represent more than one job, so the checkpoint rejects any listed incomplete job. If a future fan-out path is added, it must publish the complete expected job set in `queued_run_json` before any job can complete; incremental registration after an earlier job result is not covered by the current single-job runtime contract.

No configuration knob was added. Migration is additive; rollback leaves `success_checkpoint_json` and other added columns in place. VPS migration, same-host DB sharing, busy-recovery observation, and representative 2-core/2-GiB performance remain unverified and are not implied by the local tests.

### PR #27 checkpoint and provider-boundary follow-up (2026-10-09)

#### Confirmed code mismatch and correction

- **V2 corrupt checkpoint hotloop:** `claim_next_task` intentionally preserves attempts and permits recovery when `success_checkpoint_json` is nonempty so a valid success can recover on the final attempt. Before this follow-up, `get_success_checkpoint` raised for malformed JSON or an invalid manifest, then the worker's generic exception path called retrying `fail_task`. The unchanged nonempty checkpoint therefore preserved the attempt count and could be claimed again indefinitely. `get_success_checkpoint` now classifies decode/validation failures as `InvalidSuccessCheckpoint`; the worker uses a claim-token-fenced terminal update with status `failed`, error code `success_checkpoint_recovery_failed`, `retryable=false`, and a cause type. The update clears the stale claim fields but leaves `success_checkpoint_json` byte-for-byte intact, leaves `result_json` untouched, and performs no repository restore, orchestration, provider call, or billing. Ordinary errors and valid checkpoint recovery keep their existing retry behavior. A valid complete checkpoint remains recoverable when `attempts == max_attempts`.
- **V2 provider HTTP boundary:** a shared HTTPX request hook calls `task_queue.ensure_current_claim()` immediately before every request. The hook is installed on the OpenAI SDK client, Doubao and Gemini adapters, and shared output-URL image download. OpenAI SDK hidden retries are disabled; its existing bounded explicit retry loop remains, and SDK-wrapped stale-claim errors are unwrapped before provider error mapping. This prevents retry/fallback from misclassifying claim loss. The check does not hold a SQLite write transaction during network I/O. A request that has passed the check or is already in flight cannot be revoked remotely; the generation service's existing post-provider check still blocks stale local persistence and billing, and the next HTTP request is checked again.
- **V1 ASGI cancellation diagnostic:** the probe used the actual FastAPI app and `/v1/image/jobs` plus `/v1/image/jobs/{job_id}/revise`, a real temporary `GenerationLease`/heartbeat, and fake runner/provider work. The outer ASGI request task was cancelled while sending the response body, after the runner had entered. Both runners had started before cancellation; lease rows were released, heartbeat threads stopped, and a new lease was available. This did not reproduce the suspected “runner never starts and lease leaks” failure for that cancellation timing. No V1 runtime change was made; this evidence does not cover cancellation before the runner's first instruction.

#### Compatibility, configuration, migration, and rollback

This follow-up adds no setting, public API field, response schema, or database column. The only durable-state change is the status/error transition for a checkpoint that fails integrity validation; the checkpoint and existing result evidence are preserved. Existing valid queued-run and provider flows continue without an API change. ### V1 pre-runner ASGI cancellation addendum (2026-10-09)

The earlier V1 diagnostic cancelled requests only after the background runner had entered. Its result did not establish the before-runner case. A focused follow-up exercised the actual `/v1/image/jobs` route and the existing API-access `BaseHTTPMiddleware`, with a test-only ASGI send barrier inserted inside that middleware on the final response-body send. The route had already acquired and transferred a real SQLite lease, while the test verified the runner's first instruction had not executed. The lease row had a live TTL and its heartbeat advanced while the response send was held.

The unmodified implementation reproduced the defect: cancelling the outer ASGI request while the inner response send was held left the SQLite lease row active and renewing its TTL, and a new slot could not be acquired. An outer socket-send barrier alone was insufficient because the API-access `BaseHTTPMiddleware` allowed the background runner to start before that outer send was reached.

The V1 fix records the acquired lease in the request ASGI scope and installs a small ASGI cleanup middleware inside the API-access middleware. If response delivery or the inner application is cancelled or raises before the background task starts, the cleanup middleware calls the existing shielded `GenerationLease.release_async()`. Normal runner completion still releases through its existing `finally`; lease acquisition, SQLite schema, TTL, and public responses are unchanged. The regression verifies cancellation before runner start, cleanup of the SQLite lease, and successful acquisition of the next slot.
