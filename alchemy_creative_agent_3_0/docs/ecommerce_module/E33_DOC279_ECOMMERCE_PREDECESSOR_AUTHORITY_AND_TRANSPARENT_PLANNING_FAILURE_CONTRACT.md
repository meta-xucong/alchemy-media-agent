# E33 / Doc279 E-Commerce Predecessor Authority And Transparent Planning Failure Contract

## 1. Purpose

Doc279 closes a narrow continuation-authority defect in Professional
E-Commerce. An exact, server-authenticated E32 opaque Provider hold can be
incorrectly hidden by a later Job that stopped before any Provider image-edit
execution. The later record is append-only history, but its absence of
execution must not erase a still-current exact remediation for the same
project command.

This is not a retry policy, a Provider workaround, a policy classifier, a
prompt rewrite, or a product/People reference repair. It does not infer a
policy conclusion from an opaque 4xx and does not change a person's age,
garment facts, product truth, route, or reference channels to seek a result.

## 2. Authority Order And Scope

1. Doc263/264 remain the complete canonical product-original admission
   authority. Doc279 never narrows the pool or asks for a re-upload of an
   already admitted original.
2. Doc93/Doc269 retain locked People identity and final physical-plan
   authority. Doc265 remains the only explicit generated continuation channel.
   Generated/review history and Visual Assets never become product candidates.
3. Doc271 explicit, attributable Provider-policy closure has first precedence.
   Its `delivery_route_unavailable` operation is unchanged.
4. Doc278 remains the only authority for a zero-pixel opaque
   `image_edit_invalid_request_unattributed` hold. Doc279 only decides whether
   a later non-executed record is transparent while locating the newest valid
   Doc278 predecessor.
5. The consumer is Professional E-Commerce only. General and Photography do
   not consume E33 records, operations, UI messages, or scanning rules.

## 3. Predecessor Semantics

Project Mode scans same-project history from newest to oldest. A readable
successor is authoritative and ends scanning when any of these are true:

- it has a delivered pixel/output record or readable output file;
- it has verified Provider execution evidence, including a nonzero
  `outer_request_count`, a materialization/execution audit, or a Provider
  terminal attempt;
- it is still a current planned, generating, reviewing, or finalizing Job, or
  it has settled successfully; a live or delivered successor is never
  transparent merely because an older E32 record has equivalent facts;
- it is a completed/admitted command whose authoritative create-time binding
  differs from the current command; or
- its status, bindings, provenance, or terminal facts are missing,
  malformed, foreign, or otherwise cannot prove transparent pre-dispatch
  termination.

Only one narrow successor may be skipped: a typed,
server-issued `doc279_ecommerce_transparent_predecessor_receipt_v1` stored in
the fixed private Project Mode namespace
`doc279_ecommerce_transparent_predecessor_receipts`. It is bound directly to
the same project and durable Job, E-Commerce template, command binding,
current reference/source/admission binding, locked People binding,
selected-continuation admission, requested output count, and configured
Provider route/source-resolver identity. It must also prove all of the
following:

- terminal `planning_failed` occurred before Provider materialization and
  dispatch;
- zero Provider outer requests, no execution audit, no Provider terminal
  attempt, and no output/pixel record exist;
- the later Job's complete re-derived create-time facts equal the currently
  requested E-Commerce command; and
- its canonical receipt digest covers every preceding fact and the durable Job
  identifier.

The Product API/Project Mode terminal writer may append this receipt only after
reading the durable blocked Job, current output store, actual file records,
and execution audit. Current output/pixel/file and Provider execution checks
always outrank any stored receipt field. Browser metadata, job warning text, a
self-consistent copied dict, request fields, or keywords cannot create,
complete, update, or select it. The receipt is excluded from all public
Project and Job projections. A malformed/foreign/partial receipt fails open:
Project Mode permits a deliberate fresh command and never resurrects an older
E32 hold from it.

The receipt is not a `record.request.metadata` convention. Its fixed private
namespace is the only E33 storage authority; a browser-shaped E33 object may
be persisted incidentally with a request but remains inert even when it
contains a recomputed digest. Receipt verification independently re-reads the
bound Job/project relationship, exact private digest, source/admission,
locked-People and continuation bindings, route identity, `outer_request_count`
and terminal-attempt/materialization audit before it can make a successor
transparent.

The Project Store must explicitly allow
`doc279_ecommerce_transparent_predecessor_receipts` through its
append/list-private-record API. That API freezes nested JSON-compatible data
on append and return, preserves an idempotent exact receipt across persistent
reload, and rejects conflicting same-identity records. E33 runtime writers and
scanners must use only that API. A test may insert a direct private backing
fixture solely to represent historical state that already exists; it is never
a permitted runtime write path.

Doc277 `planning_failed` is a separate project operation, not a Job receipt.
The real background worker may receive a Product API response with both a
durable `job_id` and `status=blocked`, then persist
`planning_preflight_blocked`. Therefore E33 must neither require a Doc277
Job association nor infer that `planning_failed` means no Job was created.
When that operation coexists with a Job, only the successor Job's strict
server-owned E33 evidence and re-derived no-execution facts decide
transparency.

The skipped record does not become a new command receipt. After it is skipped,
Project Mode may recognize only the newest fully verified E32 receipt with
equivalent current deterministic facts. E32 still authenticates historical
Doc269 physical plans as evidence of what was sent; Doc279 never constructs,
reuses, or compares a new physical plan before Brain.

## 4. Pre-Create Comparison

Before idempotency, Product API creation, Brain planning, physical
materialization, or Provider dispatch, the E32 comparator may compare only:

- exact E-Commerce template;
- canonical project goal and explicit command direction;
- requested output count;
- current canonical product/source-library and full admission binding;
- locked People binding and explicit Doc265 selected-continuation admission;
- configured Provider capability/model/operation/route and source-resolver
  identity/version where selection may vary.

An exact verified E32 predecessor returns the existing sanitized no-Job
operation:

```json
{
  "state": "ambiguous_provider_request_hold",
  "terminal": true,
  "pending": false,
  "next_actions": [{"id": "review_generation_conditions"}]
}
```

It creates no Job, does not append `project.job_ids`, and performs zero Product
API create, Brain plan, physical materialization, Provider dispatch, automatic
retry, reroute, or historical replay. Changed count, source/admission,
locked-People binding, selected continuation, goal/direction, or route/source
resolver facts deliberately fail open to a fresh command.

## 5. Project And Browser Projection

For E-Commerce only, a verified transparent successor cannot allow a
coexisting Doc277 `planning_failed` operation to project ahead of its matching
E32 remediation. The project response must expose only the E32 safe operation
and must never expose historical Job IDs, provider errors, source IDs, paths,
hashes, evidence digests, or private operation bindings.

The same rule applies to the browser HTTP/background path when the exact E32
pre-create gate returns its sanitized no-Job `blocked` response. The worker may
retain its append-only private Doc277 `planning_preflight_blocked` operation,
but its public readback must project the already verified E32 operation rather
than `planning_failed`. This override is narrow: it is available only after a
matching E32 receipt was located through a same-fact, zero-execution E33
successor. An ordinary Doc277 failure, a malformed successor, a changed
command, or a later authoritative Job continues to project
`planning_failed`.

An ordinary Doc277 planning failure remains a `planning_failed` terminal
operation. Its desktop/H5 text must say that planning stopped before an image
request was sent and that project history was retained. It must not claim that
no Job was created. It clears busy/loading, progress and recovery timers,
shows one local review action, and does not POST automatically.

For the transparent predecessor case, desktop/H5 must atomically settle the
same terminal state and show only E32's
`review_generation_conditions` action. It must not show preparing, generating,
recovering, a duplicate planning action, or raw diagnostics.

## 6. Historical Compatibility

Historical jobs remain append-only. A sufficiently complete historical E32
record may be recognized read-only only after strict E32 verification. A
historical planning failure is transparent only when complete E33
server-issued evidence is present and re-verifies against current facts.
Incomplete legacy records, copied records, and browser-shaped data do not
block new commands and do not mutate history during readback.

## 7. Phase 0 Boundary

Phase 0 changes only this contract, the E-Commerce index, and deterministic
local red tests. Tests use in-memory Project Mode/Product API stores, fake
no-pixel Providers, and local browser fixtures. They do not call Provider,
MCP, ImageGen, VPS, or live projects/jobs/outputs.

Phase 1, after audit, may issue the narrow server-owned evidence on a
blocked-before-image-dispatch E-Commerce Job, including the actual Doc277
background-worker `job_id + blocked` path. The terminal writer must verify the
actual Job has no Provider execution, terminal attempt/materialization audit,
pixel/output/file before appending the private receipt; a request metadata
field is never a substitute. The write is explicit: before the worker it has
no E33 receipt; after a verified terminal re-read it appends exactly one
server-authoritative receipt through the Project Store API. Phase 1 then adds
the predecessor scanner,
project projection precedence, and terminal UI copy. It must preserve all
Doc268 receipt ownership, Doc271 precedence, and Doc278 sanitization
invariants.
