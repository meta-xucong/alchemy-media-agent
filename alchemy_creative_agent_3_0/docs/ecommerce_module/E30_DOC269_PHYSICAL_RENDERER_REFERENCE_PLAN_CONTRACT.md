# E30 / Doc269 Physical Renderer Reference Plan Contract

Status: Phase 0 observation and deterministic red-contract authority

## 1. Scope And Observed Mismatch

This document governs the final physical image-reference list for a
Professional E-Commerce output. It is a specialized E-Commerce Product API to
Provider materialization contract. It does not alter the General Template,
Photography, Product Truth admission, People Visual Asset authority, selected
continuation authority, review ownership, or browser submission behavior.

Read-only production evidence for `project_65432102a2` and
`job_4c86f8fb7b` established these facts:

- Doc263 selected one physical product projection for the output from the
  current four-product original pool.
- The locked People Visual Asset carried three approved formal face-identity
  evidence outputs.
- No generated output was selected as a continuation direction.
- The upstream `image_edit` telemetry recorded physical
  `reference_count=10`, although `ProductionImageGenerationProvider` declares
  a five-image capability limit.

The source intent is therefore one selected product plus three locked face
sources, or four physical renderer references. The ten-input result proves
that the final materialization is not yet governed by one exact physical plan.
It does not prove that either `uploaded_assets` plus `reference_assets` alone
caused every duplicate: Provider derivative expansion is also on the observed
path. No claim is made that input count alone explains the upstream `400` or
any possible policy decision. The historical job must not be replayed.

## 2. Authority And Boundary

For a Doc263-authorized Professional E-Commerce output, Product API owns one
immutable `PhysicalRendererReferencePlan` per output before Brain/provider
execution. The final Provider materializer verifies and consumes that plan.
The plan is the sole physical-input authority at these two equivalent
observability points:

1. `asset_plan.provider_input_plan.reference_image_asset_ids` and its typed
   physical-reference entries.
2. `_materialized_provider_reference_assets`, followed by the Web image
   adapter's `reference_image_paths` input.

The two projections must be exactly equal in order, content, and physical
count. A pre-plan admission list, generic metadata list, adaptive selector, or
derivative helper is supporting evidence only. None may append, replace,
expand, or silently trim the final plan after it is frozen.

Each typed entry contains, at minimum:

- stable source ID and physical reference ID;
- E-Commerce role and channel (`product_truth`, `people_identity`, or the
  separately admitted selected-continuation channel);
- output index and the Doc263 job/projection binding where applicable;
- readable file path, actual content SHA-256, MIME type, and source lineage;
- immutable order and the capability-count reservation.

The server verifies file readability and actual digest before materialization.
The Web adapter receives the same verified file sequence, not a recomputed list
from `uploaded_assets`, `reference_assets`, history, or an adapter-side cap.

## 3. Required Professional E-Commerce Behavior

### 3.1 Default physical plan

For a Professional E-Commerce output, the plan always begins with the one
Doc263 `PhysicalProductReferenceProjection` selected product original in
`product_truth`. A project-owned People Visual Asset is not itself permission to
append face evidence. `people_identity` entries may be added only after the
remote Brain's typed `visual_task_profile.subject_entities` declares a visible
person for the target output and the Product API has frozen the approved People
Visual Asset identity binding. Prompt keywords, product filenames, browser
labels, upload order, and historical generated outputs are not authority for
adding `people_identity`.

The other active product originals remain canonical Product Truth pool evidence
for Product API/Brain/review. They are not physical renderer inputs for this
output. Locked face evidence remains People identity evidence and cannot be
promoted into product-root truth, product clustering, or adaptive product
selection, and it must not be auto-promoted from history or an active People
binding when the Brain has not declared a visible person.

### 3.2 Selected continuation

An explicit user-selected generated continuation remains in its existing
Doc265 selected-continuation channel. It is never inferred from generated or
review history, a timeline, a prior output, or a generic reference list. When
it is explicitly selected and its binding is readable, it may enter the typed
plan only through that existing contract and only if the complete plan fits the
negotiated physical reference cap. The default has no continuation entry.

### 3.3 Fail-closed materialization

Duplicate source/content, role/channel drift, missing/unreadable file, digest
mismatch, malformed output binding, a mismatch between frozen plan and final
asset plan, or physical count above the negotiated cap closes the command
before Brain or Provider dispatch as applicable to the information available at
that boundary. There is no silent trimming, derivative expansion after cap
reservation, implicit fallback reference, auto retry, or automatic resubmit.

The public result is a sanitized actionable E-Commerce state. It does not leak
paths, hashes, output IDs, or Provider internals. Durable history remains
unchanged and readable.

### 3.4 Provider isolation

For a Doc263 E-Commerce contract, Provider consumes and verifies the typed
per-output plan directly. It must not recombine generic `uploaded_assets` and
`reference_assets`, then apply generic derivative/adaptive expansion, to form
physical Web image inputs. Generic and Photography continue using their
existing Provider behavior. This document neither relaxes the five-image
capability nor changes ordinary route capability negotiation.

## 4. Compatibility And Security

- Doc263 `ProductTruthAdmission` and
  `PhysicalProductReferenceProjection` remain the product authority.
- Doc264/265 canonical-current references, legacy compatibility, and explicit
  selected-continuation validation remain authoritative in their own channels.
- Doc267 locked People identity and manual-review closure remain authoritative.
- Historical jobs and outputs are append-only. This correction does not repair,
  delete, replay, or reclassify `job_4c86f8fb7b`.
- Browser fields cannot author physical references, role/channel labels,
  binding digests, content digests, or capacity reservations.

## 5. Phase Boundaries

Phase 0 supplies only this correction model and deterministic local red tests.
It calls no Provider, MCP, ImageGen, VPS, or production route, and changes no
runtime behavior.

Phase 1 may add the typed per-output plan at the owning Product API lifecycle
boundary, route its verified projection through Provider materialization, and
make the Web adapter consume that exact sequence. It must add compatibility
reads for valid historical records without rewriting them, preserve Doc263-268
authority, and prove Generic/Photography isolation. Production validation is a
separate guarded phase after review.

## 6. Acceptance Matrix

1. Actual Project Mode/Product API construction with four product originals
   and a locked three-face People card produces one selected product plus the
   three identity sources only when the remote Brain typed profile declares a
   visible person and Product API freezes the People identity binding. A command
   without that Brain declaration produces the one selected product source and
   no People or generated-history input.
2. `reference_image_asset_ids`, typed final entries,
   `_materialized_provider_reference_assets`, and Web adapter file inputs are
   equal in order and count, with physical count one when no visible person is
   Brain-declared and four when the approved People identity binding applies.
3. Non-selected product originals and unselected generated/review history do
   not enter the final physical plan.
4. A continuation appears only after an existing explicit selection receipt;
   default construction contains none.
5. Duplicate, drifted, missing, digest-mismatched, or over-cap plans close
   before adapter/Provider dispatch with no retry and a sanitized state.
6. Product Truth, People identity, Generic, and Photography regression suites
   remain unchanged.
